# 评委视角终审发行版设计

- 日期：2026-08-18
- 状态：已完成讨论，待书面复核
- 适用项目：XH-202613 面向雄安新区“城市大脑”的车路云一体化协同管控算法与仿真平台
- 赛道：功能三赛道 B（经典交通控制算法适配与优化）

## 1. 文档地位

本文定义项目终审发行版的现行目标、系统边界、算法、实验、可视化和验收口径。旧设计、任务书、进度表或历史报告与本文冲突时，以本文和当前可复现证据为准。

终审发行版只面向评委和复现者，不展示成员代号、项目分工、周任务、内部进度、开发路线、临时验证脚本或未经重新验证的历史结论。报告、PPT 和演示视频在项目与正式实验冻结后制作，其数字和结论必须来自冻结证据。

## 2. 目标与成功标准

项目目标是在主办方提供的 20 个真实路口数据上，交付一个可一键启动、可切换场景、可替换算法、可实时观察、可批量复现实验的交通信号控制平台。

成功必须同时满足以下条件：

1. Windows 普通用户可通过原生一键启动进入评委端 Web 控制台。
2. Docker 路线可用于跨系统复现和部署，但不作为评委首次使用的唯一入口。
3. 20 个官方路口可导入、校验、运行和切换，官方原始数据始终只读。
4. 固定配时、经典 MaxPressure 和容量感知 MaxPressure 通过统一插件接口运行。
5. 云、边、车在单机内具有真实的逻辑边界、消息契约、延迟、校验和回退，而不是仅使用概念命名。
6. 正常与扰动实验可恢复、可审计、可统计，所有结论能够追溯到单次运行产物。
7. Web 能展示 SUMO-GUI 的近实时画面、关键指标、算法对比和历史结果；画面故障不影响控制和证据记录。
8. 最终发布包不包含内部协作文档、无效旧实验、缓存、个人路径、临时文件或不受支持的完成声明。

## 3. 需求边界

### 3.1 PDF 对齐范围

系统覆盖赛题要求中的真实场景问题导入、仿真环境适配、算法部署、车路云协同控制、效果比较、效率评价、安全评价、能耗评价、燃油消耗统计和道路受阻类扰动支持。

PDF 对安全和能耗提出评价方向，但没有逐项规定碰撞、闯红灯、非法相位转换、急减速、瞬移和冲突事件的具体阈值。因此本文将前三项零容忍定义为项目安全硬门槛，将后三项定义为项目工程观察指标。报告中必须明确区分“PDF 明示要求”和“项目自定义工程标准”。

### 3.2 本阶段范围

- 整理现有代码结构和对外入口，不重写已可复用的仿真核心。
- 修复流量变体、完成车辆指标、版本元数据和运行生命周期等已知问题。
- 建立场景包、算法插件、实验协议、证据合同和评委端 Web 控制台。
- 提供原生启动、Docker、自动测试、正式实验和干净发布包。
- 项目与证据冻结后，再生成报告、PPT 和 5–8 分钟视频。

### 3.3 非目标

- 不制作营销落地页。
- 不制作三维数字孪生或与评分无关的装饰性大屏。
- 不故意制造车辆碰撞来展示事故。
- 不修改或覆盖 `赛题资料.7z` 和官方原始路口数据。
- 不预先宣称容量感知 MaxPressure 必然优于其他算法。
- 不把 100 步安装冒烟运行当作正式实验。

## 5. 组件职责与接口

### 5.1 启动与发布层

原生启动器负责环境预检、依赖定位、端口选择、FastAPI 生命周期和浏览器打开。它必须输出明确的成功或失败原因，并提供诊断日志。Docker 使用同一应用入口和配置，不维护第二套业务实现。

### 5.2 场景目录与导入服务

场景服务扫描官方 20 路口并生成只读目录。每个可运行场景通过标准场景描述引用路网、流量、路线、转向、配时、高精地图和 SUMO 配置，不复制后失去来源关系。

导入其他路口时执行结构化解析和校验，生成包含来源路径、SHA-256、SUMO 兼容性、步长、信号灯、车道和配置引用的标准场景包。导入失败不得留下可运行的半成品场景。

交通负载或扰动通过临时派生变体实现。变体记录父场景、参数、生成时间和输入哈希；运行结束后可按保留策略清理。流量倍率只能缩放既有需求定义，不能同时保留原流量并追加一套重复流量。

### 5.3 算法插件注册表

所有算法通过一个中心注册表暴露稳定标识、显示名、配置模型、能力信息和工厂函数。API、Web、批量实验和命令行只依赖注册表，不硬编码算法工厂。

插件必须实现统一生命周期：初始化场景、接收观测、输出候选动作、重置状态。新增算法不应要求修改运行服务的分支逻辑。

### 5.4 云-边-车协同链路

- 云层：接收聚合状态，计算周期性策略或参数下发，并记录消息时间。
- 边层：执行具体信号控制算法，在云消息缺失或超时时继续本地控制。
- 车端/路侧层：通过 TraCI 采集车辆、车道和信号状态，执行已验证动作并反馈结果。

层间使用现有类型契约和事件记录扩展出明确消息信封，包含运行标识、仿真时间、发送时间、有效期和载荷版本。链路支持可配置延迟、过期消息丢弃、输入校验和确定性回退。单机部署不伪装成真实分布式网络，但行为边界可独立测试。

### 5.5 运行服务

运行服务拥有 SUMO 进程、运行状态机和唯一写入权。单次运行状态至少包含 `queued`、`starting`、`running`、`stopping`、`completed`、`failed` 和 `interrupted`。

切换路口时，服务先拒绝新动作，向当前 SUMO 发出安全停止，落盘中断清单并释放进程，然后启动新场景。Web 服务本身不重启。任何退出路径都必须关闭 TraCI、等待或终止所属 SUMO 子进程，并完成可解析的终态记录。

### 5.6 指标与证据服务

实时指标和最终指标共享同一语义来源。单次运行产物使用独立目录，至少包含配置快照、来源清单、环境版本、事件、逐步或聚合指标、最终摘要、日志和状态。批量汇总只读取已完成且通过结构校验的单次运行。

## 6. 算法方案

### 6.1 固定配时

固定配时从官方 Excel 或标准场景配置读取计划，作为可解释基线。缺失或非法配时必须在启动前报告，不静默替换为任意默认值。

### 6.2 经典 MaxPressure

共享状态适配器从 SUMO 受控连接建立 movement `m = (i, j)`，其中 `i` 是进口车道、`j` 是出口车道。令 `q_i`、`q_j` 为停车排队车辆数，`s_m` 为该 movement 的有效饱和服务率，则合法绿色相位 `p` 的经典压力固定为：

```text
P0(p) = sum(s_m * (q_i - q_j), m in movements(p))
```

算法选择压力最大的合法绿色相位；并列时依次优先保持当前相位、较小相位索引，保证确定性。经典基线不使用容量归一化、出口阻塞阈值、EWMA、云端动态绿灯或其他项目增强。`s_m` 优先由可追溯道路参数得到；参数不足时通过冻结的饱和需求校准得到；只有两者均不可用时才使用统一默认值，并执行敏感性分析。

导入场景若无法从 `getControlledLinks()` 和路网连接得到完整 movement 映射，则不能进入正式矩阵。现有感应控制可以作为开发辅助算法保留，但不能改名代替经典 MaxPressure。

### 6.3 容量感知 MaxPressure

令 `C_i`、`C_j` 为按可用车道长度和冻结车辆占用长度计算的储车容量，则容量归一化压力固定为：

```text
P1(p) = sum(s_m * (q_i / C_i - q_j / C_j), m in movements(p))
```

容量必须大于零；无法获得容量的场景预检失败，不允许在同一正式矩阵内混用绝对排队和归一化排队。下游车道占有率达到冻结阈值时，对应 movement 暂停放行；一个相位仍有未阻塞 movement 时可以参与选择，所有候选 movement 均受阻时保持安全状态并记录网格锁风险事件。

容量感知版本按 `M0` 经典压力、`M1` 容量归一化、`M2` 下游溢出保护、`M3` 统一安全执行层、`M4` 可选短时预测逐层实现和消融。绿灯时长只在场景最小值和最大值之间按选中压力相对平均正压力调整。它必须输出 movement 压力分量、阻塞原因、选择原因和最终动作，便于 Web 展示与实验审计。

EWMA 或其他预测只作为可消融增强项。只有在预先冻结的消融实验中表现稳定、未破坏安全门槛且对多数场景有正向效果时，才进入默认容量感知算法；否则保持关闭并如实报告。

### 6.4 动作安全校验

算法输出先进入独立校验器，再写入 TraCI。校验器根据场景信号方案执行最小绿灯、黄灯、全红时间、合法相位和动作时效检查。非法或过期动作被拒绝并记录，控制回退到当前安全相位或场景固定配时。算法不能绕过校验器直接写信号灯。

## 7. 场景与扰动

正常负载使用 `1.0` 和 `1.25` 两档。扰动实验包含：

1. 施工占道：关闭或限制指定车道，表示道路受阻。
2. 大型活动：按冻结规则改变入口需求分布或总需求。
3. 车辆故障：停驶车辆造成车道阻塞，但不故意触发碰撞。

每个扰动必须声明开始时间、结束时间、作用对象、强度和恢复方式。扰动场景是临时变体，不修改父场景。正式运行前先验证路线连通性和信号可执行性。

## 8. 实验设计

### 8.1 正常实验矩阵

```text
20 个路口 × 3 个算法 × 2 个负载 × 3 个种子 = 360 次
```

- 算法：固定配时、经典 MaxPressure、容量感知 MaxPressure。
- 负载：`1.0`、`1.25`。
- 随机种子：`42`、`43`、`44`。

### 8.2 扰动实验矩阵

```text
20 个路口 × 3 个算法 × 3 类扰动 × 1 个固定种子 = 180 次
```

正式实验总计 540 次。扰动矩阵固定使用种子 `42`，每类扰动参数在预实验后冻结。

### 8.3 仿真时长

- 正式运行：3600 仿真秒。
- 预热期：前 600 仿真秒，不进入评价指标。
- 评委快速模式：600 仿真秒。
- 安装冒烟：100 个实际仿真步，仅证明环境和最小链路可启动。

步数与仿真秒的换算必须以场景 `step-length` 为准。`1.0 s` 步长场景的正式运行是 3600 步、预热期是 600 步；`0.1 s` 步长场景分别是 36000 步和 6000 步。运行器的正式接口只使用仿真秒表达时长，并在清单中记录换算后的实际步数，避免不同步长场景被误跑成十倍时长或十分之一时长。

### 8.4 统计规则

同一路口、负载和种子形成配对比较。报告差值、相对变化、效应量和 95% 置信区间，同时报告 40 个“路口 × 负载”单元中的改善占比。

一个算法只有同时满足以下条件，才可以在正常实验中表述为总体更优并成为默认候选：全部正式运行通过安全硬门槛；相对对照算法的平均行程时间配对差值 95% 置信区间上界小于 0；至少 21 个“路口 × 负载”单元的三种子均值优于对照。候选算法还必须报告最差单元及其退化幅度。若没有算法满足条件，默认使用官方固定配时并将其他算法保留为可选项。

扰动实验单独给出韧性结论，不与正常实验混成一个总分。样本不支持预期结论时修改结论，不改变样本选择或隐藏不利结果。

## 9. 指标定义

### 9.1 主要与支持指标

- 主要指标：完成行程车辆的平均行程时间。
- 支持指标：平均与 P95 排队长度、平均等待时间、吞吐量、通行能力和完成率。
- 未完成车辆：单独报告数量、占比和运行结束时状态，不计入吞吐量、完成行程时间、完成行程延误、停车次数、燃油或 CO2 的完成车辆统计。

如需报告全系统累计能耗，必须将完成车辆和仍在网车辆分项列出，不能把二者混入完成行程均值。

### 9.2 安全门槛与观察指标

安全硬门槛：

- 碰撞数为 0。
- 红灯违规数为 0。
- 非法相位转换数为 0。

工程观察指标：急减速、车辆瞬移和潜在冲突事件。观察指标必须报告，但在阈值经预实验冻结前不伪装成 PDF 规定的淘汰阈值。只要安全性明显恶化，即使平均行程时间下降，也不能判为更优。

### 9.3 能耗指标

燃油消耗和 CO2 排放分别统计，不以单一合成分数替代。每项同时保留总量、每完成车辆均值和适用的距离归一化口径，并注明 SUMO 输出来源和单位。

## 10. 评委端 Web 控制台

### 10.1 信息架构

Web 第一屏直接进入可用控制台，不制作营销首页。控制台包含四个视图：

1. 实时仿真：选择场景、算法、负载和扰动，控制运行并查看实时状态。
2. 算法对比：比较同条件运行的效率、安全和能耗指标，显示结论依据。
3. 历史结果：检索运行记录、正式实验、置信区间和证据来源。
4. 场景管理：查看官方场景、导入场景、校验结果、来源和哈希。

前端采用 `web/` 下的 React、TypeScript 和 Vite 单页应用，生产构建作为静态资源由 FastAPI 同源提供。Node.js 只用于开发和构建，原生发行包包含已构建资源，评委运行时不需要安装 Node.js。图表和图标依赖随发布包本地提供，不依赖公网 CDN。

### 10.2 一键评委演示

一键演示使用冻结的代表性雄安场景，按以下顺序自动执行：

```text
场景与问题说明
  -> 固定配时运行
  -> 容量感知算法运行
  -> 实时指标与信号决策
  -> 同条件结果比较
  -> 有证据限定的结论
```

演示不得使用与正式指标口径不同的隐藏规则。若预计算结果可用，界面可以在实时运行同时展示已冻结的正式证据，但必须清楚标识“当前快速运行”和“正式实验结果”。

### 10.3 SUMO 画面集成

默认方案不把 SUMO 的 Qt 原生窗口强行设为浏览器子窗口。后端通过 TraCI 启动和控制 `sumo-gui`。运行线程按自适应间隔调用 SUMO GUI 截图接口，将最新 PNG 帧交给容量为 1 的内存发布槽；Web 通过独立画面端点获取实际 SUMO-GUI 视图。任何 Web 请求都不能跨线程直接调用 TraCI。

桌面环境同时提供“打开原生 SUMO-GUI”按钮，用于显示或聚焦同一运行所属的原生窗口。按钮在不支持桌面窗口的环境中明确禁用。Docker 的核心复现默认使用无界面 SUMO；需要容器内画面时使用独立 GUI profile 和虚拟显示，不让 GUI 依赖阻塞核心算法复现。

本机演示的设计目标是 5–10 FPS、端到端画面延迟不高于 500 ms；这些是目标机器上的验收目标，不是未经实测的完成声明。画面队列保持有界，拥塞时丢弃旧帧，只展示最新状态。指标和控制事件独立传输，并带仿真时间戳，因此画面延迟不影响算法执行。

批量正式实验默认使用无界面 `sumo`。画面采集失败时，Web 明确显示降级状态并继续提供指标；控制运行和证据落盘不得依赖画面流成功。

## 11. API 与实时通信

现有 FastAPI 接口继续作为唯一后端入口。对外接口按场景、算法、运行、实验、结果和系统状态分组。运行创建请求引用算法注册表标识和场景标识；状态查询返回稳定运行状态机；停止请求为幂等操作。

实时指标和事件通过 WebSocket 发布，SUMO PNG 画面使用独立的最新帧端点并携带 `run_id`、帧序号和仿真时间。大体积图像与结构化指标分开传输，避免慢画面阻塞控制状态。API 模型、OpenAPI 文档和前端类型由同一合同生成或校验。

## 12. 证据与产物合同

每次运行使用不可冲突的 `run_id`，并保存：

- `manifest.json`：运行身份、代码版本、场景、算法、参数、种子、负载、扰动和时间。
- `provenance.json`：原始输入路径与哈希、标准场景包版本、SUMO/Python/依赖版本。
- `status.json`：状态机终态、开始与结束时间、失败或中断原因。
- 事件与指标文件：采用冻结字段、单位和缺失值语义。
- 日志：只保存该运行相关诊断，不混入其他运行。

汇总和报告生成器必须记录输入清单、生成命令、代码版本和输出哈希。旧 `output/evidence` 生成物和 `verify_route*` 内部脚本不进入最终证据合同；在替代验证完成后与引用它们的内部材料一起删除。

## 13. 错误处理与恢复

- 环境预检失败：不启动仿真，显示缺失依赖和修复入口。
- 场景校验失败：保持官方数据不变，拒绝注册失败的导入场景。
- 算法异常：记录异常和最后合法状态，执行固定配时或保持安全相位回退。
- 云消息延迟或过期：边层继续使用最后有效参数或本地默认参数。
- SUMO/TraCI 断开：运行标记为失败或中断，清理所属进程并保留已生成证据。
- Web 或画面流断开：仿真按后端策略继续；重连后从最新状态恢复，不回放过期帧。
- 批量实验单项失败：保留失败记录，只定向重跑失败组合，不覆盖已完成结果。
- 磁盘空间不足：在启动新运行前预警并拒绝会导致不完整证据的任务。

## 14. 测试与验收

### 14.1 自动测试

- 单元测试：算法压力计算、注册表、相位安全校验、指标语义、场景解析和变体生成。
- 契约测试：API、事件、运行清单、云边车消息和 OpenAPI 一致性。
- 集成测试：MockBridge 生命周期、真实 SUMO 单路口、运行停止与切换、失败清理和中断恢复。
- Web 测试：四个视图、运行操作、断线重连、错误状态、长文本和常用桌面分辨率。
- 发布测试：原生启动、Docker 构建与健康检查、干净目录解压运行。

### 14.2 分级真实验证

1. 路口 1 执行 100 步安装冒烟。
2. 路口 1 执行评委快速模式，核对控制、画面、指标和证据。
3. 20 个路口执行短时预检，验证导入、相位和进程清理。
4. 代表性路口执行三算法正式时长预实验，冻结参数和口径。
5. 执行 360 次正常矩阵和 180 次扰动矩阵。
6. 在目标 Windows 环境测量 SUMO 画面帧率和延迟。
7. 在 Docker 和至少一个第二环境执行复现验证；未实际执行时状态必须为 `not_run`。

### 14.3 完成判定

测试代码存在不等于通过，历史报告不等于当前证据。每项验收只允许 `pass`、`fail` 或 `not_run`。只有当前代码、当前环境和当前产物能够复现时才标记 `pass`。

## 15. 发布结构与清理

终审发布包保留：

- 运行所需源代码、配置、20 路口官方数据引用和标准场景包。
- 原生启动入口、Docker 文件、评委运行说明和算法扩展说明。
- 冻结实验配置、正式汇总、统计结果和必要的代表性单次证据。
- 后续生成的报告、PPT 和视频交付物。

终审发布包删除或排除：

- 项目分工、成员代号、周任务、内部路线、进度表和开发会议材料。
- `verify_route*`、临时生成器、手工复核目录和仅为内部阶段验收服务的测试。
- 无法证明符合现行矩阵、算法和指标口径的旧仿真数据。
- `.venv`、缓存、临时目录、个人绝对路径、编辑器文件、密钥和重复压缩包。

删除前先建立引用清单，确保对外文档、测试和启动入口已迁移到新合同。官方压缩包、原始场景和用户现有修改不因清理被覆盖。

## 16. 实施顺序

1. 冻结现状与建立可靠测试环境。
2. 修复仿真输入、指标和元数据正确性问题。
3. 建立场景包、算法注册表和运行生命周期边界。
4. 完成经典 MaxPressure、容量感知 MaxPressure、安全校验和云边车链路。
5. 建立正式实验、统计与证据合同。
6. 实现评委端 Web、实时推送和 SUMO 画面集成。
7. 完成原生启动、Docker、跨环境验证和终审清理。
8. 冻结项目与实验后生成报告、PPT、视频和最终提交包。

每一阶段必须通过对应验收后再冻结下游成果。若代码、配置、场景或指标口径改变，受影响的实验、图表和材料必须重新生成。

## 17. 最终完成定义

项目只有在以下条件全部满足时才完成：评委可一键启动并操作；20 路口和三算法按统一合同运行；安全、效率、能耗和扰动证据真实可追溯；540 个预期组合均有唯一成功产物且不存在缺失、重复或未解决失败；Web 与 SUMO 可视化达到目标环境验收；原生和 Docker 路线得到真实验证；终审包完成干净环境演练；报告、PPT 和视频只引用冻结事实；发行版不包含内部协作材料。
