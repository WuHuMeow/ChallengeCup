# 内部文档与项目 PDF 对齐设计

**日期：** 2026-07-27

**范围：** GitHub 内部研发仓库的 README 与 Markdown 文档

**受众：** 项目团队成员，不作为最终评委展示仓库

## 1. 目标

以项目 PDF `XH-202613_面向雄安新区“城市大脑”的车路云.pdf` 为需求基线，统一仓库中的项目方向、当前实现、IA/IB 验收状态、复现入口和历史文档定位。文档应帮助团队快速判断以下事实：

1. 功能一和功能二是共同基础，均需完成。
2. 功能三只需选择一个方向深入，本项目选择赛道 B（算法调优型）。
3. 当前仓库完成的是可运行代码、配置、接口、实验流程和本地验收；评委版报告、PPT 与视频将由后续独立仓库整理。
4. 已删除的大体积仿真产物不在 Git 中，复现代码、配置、审计报告与运行说明继续保留。
5. Docker 实机与第二机器复现没有真实证据时保持 `not_run`。

## 2. PDF 对齐口径

| PDF 要求 | 仓库对应内容 | 文档口径 |
| --- | --- | --- |
| 功能一：场景与数据接口 | `api/`、`core/`、`cloud/`、`engine/`、接口文档 | 必做基础，说明输入、输出、车路云数据流和 API |
| 功能一：算法与可视化仿真 | `algorithms/`、`experiments/`、`visualization/` | 必做基础，包含固定配时基线、控制策略和图表链路 |
| 功能一：智能决策模型 | CA-MP、EWMA/流量预测与调参流程 | 必做基础，说明规则、预测和传统方法对比 |
| 功能二：场景构建与导入 | `data/`、`scenes/`、`engine/configs/` | 必做基础，覆盖 20 个路口及配置生成/导入 |
| 功能二：实用模块 | V2X 通信、数据采集/可视化、算法适配器 | PDF 允许任一模块；本项目实现多项，不写成三项均为强制要求 |
| 功能二：部署与性能 | `docker/`、部署指南、压力与恢复流程 | 代码与静态契约完成；Docker live 仅在实跑后记为通过 |
| 功能三：赛道选择 | 赛道 B，CA-MP 场景适配、参数调优、性能评估 | 只宣称赛道 B，不再使用“功能三赛道”之类易混表述 |
| 答题要求 | 代码、20 路口、部署说明、实验评估、演示素材 | 当前仓库覆盖代码与复现资料；评委版文档和视频单独跟踪 |

## 3. 文档分层

### 3.1 当前事实入口

- 根 `README.md`：项目定位、PDF 对齐、快速开始、当前验收状态和文档导航。
- 模块 README：各目录职责、输入输出、依赖、最小使用方式和限制。
- `docs/README.md`：当前文档地图，区分活跃指南、验收证据和历史记录。
- `docs/guides/`、`docs/architecture/`、`docs/operations/`、`docs/reference/`、`docs/reports/`：当前可执行说明和事实资料。
- `docs/ia-ib-final-verification.md`：最终 IA/IB 验收事实来源。
- `docs/ia-ib-simulation-artifact-cleanup.md`：仿真产物删除事实来源。

### 3.2 历史记录

- `docs/superpowers/specs/` 和 `docs/superpowers/plans/` 保留当时的设计与执行记录。
- `docs/tasks/` 保留 W1-W6 周任务原文；未勾选项表示当时计划状态，不等同于当前缺陷。
- 历史文档中的旧路径、旧测试数量和旧计划不得被当作当前运行说明。
- 历史文件不进行无意义的批量改写，只修复会妨碍阅读或指向错误当前入口的内容。

## 4. 重复内容处理

`docs/tasks/` 是当前 README 使用的规范任务目录。`docs/team/tasks/` 与其高度重复且没有当前入口引用，处理规则如下：

1. 按角色和周次建立文件映射。
2. 比较内容，识别只存在于 `docs/team/tasks/` 的有效信息。
3. 将仍有维护价值的独有信息合入对应的 `docs/tasks/` 文件或任务索引。
4. 删除 `docs/team/tasks/`；历史仍可通过 Git 提交恢复。
5. 更新所有现行链接，只指向 `docs/tasks/`。

其他重复文档按相同原则处理：规范路径保留，完全重复且没有独立用途的副本删除；历史计划中记录旧路径的文本保持原貌。

## 5. 更新策略

对仓库全部 Markdown 执行审计，但不要求每个文件产生修改。修改条件包括：

- 与 PDF 的功能/赛道口径冲突；
- 与当前代码、目录、命令、依赖或测试入口冲突；
- 把已删除仿真产物写成仓库内现存文件；
- 把 `not_run` 写成已通过；
- 活跃文档链接失效或指向重复目录；
- 当前状态和历史计划没有清晰区分；
- 文件编码或正文损坏，影响团队阅读。

不修改的内容包括：

- 历史计划在当时的目标、日期和任务勾选状态；
- 与本次 PDF 对齐无关的技术设计结论；
- 源数据、配置、代码、PDF、报告素材及仿真数据生成逻辑。

## 7. 验证标准

实施完成后必须满足：

1. 全部 README 和 Markdown 能以 UTF-8 正常读取。
2. 活跃文档中的相对链接均存在；历史示例链接可明确标为历史而不是静默失效。
3. 不再存在把功能一、功能二描述为二选一的文本。
4. 不再存在把 A/B/C 三条赛道描述为同时完成的文本。
5. 当前文档统一说明本项目选择功能三赛道 B。
6. 当前文档不声称仿真原始产物仍在仓库。
7. Docker 和第二机器状态保持 `not_run`。
8. `docs/team/tasks/` 删除前已完成差异合并。
9. Markdown 格式、代码块和本地路径检查通过。
10. Python 全量测试、导入、编译和代码规范检查继续通过。

## 8. Git 工作流

文档更新在临时分支 `codex/docs-pdf-alignment` 完成。验证通过后普通合并回 `main`，删除临时本地分支并推送 GitHub `main`。禁止强推；最终本地只保留 `main`。
