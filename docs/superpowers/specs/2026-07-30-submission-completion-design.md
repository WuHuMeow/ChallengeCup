# 挑战杯项目提交收敛设计

> 日期：2026-07-30  
> 目标截止：2026-09-01  
> 执行模式：一人主导、AI 执行  
> 推进策略：提交物驱动、证据链优先

## 1. 目标与成功标准

本设计用于把当前“核心工程基本完成、正式交付尚未完成”的仓库推进到可提交状态。最终成功不以代码数量或历史任务复选框判断，而以完整提交包、可复现实验和可核验证据为准。

截至 2026-07-30，仓库已有 CA-MP、FixedTime、Actuated、SUMO/TraCI、REST API、云边消息、实验矩阵和绘图接口。当前完整测试在默认 Windows 临时目录下为 196 passed、2 failed；失败来自项目位于 D:、pytest 临时目录位于 C: 时 `os.path.relpath` 无法跨盘符。SUMO 1.27.1 可用，Docker 尚未安装，Docker live 与第二机器复现仍为 `not_run`。正式 360 组实验产物已清理，Word/PDF 报告、PPT、视频和独立演示方案尚未形成。

2026-09-01 前必须形成并核验以下成果：

1. 完整测试、编译检查、代码规范和最小 SUMO 实跑全部通过。
2. Docker live 构建、运行、导出、导入通过，并在第二台电脑完成复现。
3. 20 路口 × 3 算法 × 2 流量 × 3 种子的 360 组正式实验可追溯、可恢复、可审计。
4. 报告、PPT、5–8 分钟视频、实际场景演示方案与运行说明内容一致。
5. 最终压缩包在全新目录完成一次从解压到运行的演练，并保留至少两份备份。

## 2. 范围与非目标

必做范围包括质量门禁修复、Docker 与第二机器复现、正式实验、统计和图表、正式材料、演示视频以及最终打包。所有报告数字和图表必须来自冻结后的正式实验数据。

PyQt 看板不进入必交路径。只有在 2026-08-25 前所有必交材料均已冻结且不存在阻塞问题时，才允许评估该加分项。2026-08-26 后不修改算法核心；2026-08-29 后只修复会阻塞提交的问题，不增加功能。

## 3. 推进架构

项目采用五个顺序冻结阶段。前一阶段未通过验收，不进入后一阶段，以避免实验、报告和演示在不同代码版本之间漂移。

### 3.1 阶段一：质量基线冻结（07-30—08-02）

修复 Windows 跨盘符测试问题，统一仓库实际分支与文档中的 `master/main` 表述，核对依赖版本，完成完整测试、编译、代码规范、文档一致性和最小 SUMO 实跑。冻结结果必须绑定 Git commit、Python/SUMO 版本、执行命令和时间。

### 3.2 阶段二：部署与复现冻结（08-03—08-07）

安装 Docker Desktop，完成无缓存构建、容器启动、健康检查、仿真请求、镜像导出和重新导入。在第二台电脑上分别验证源码部署和 Docker 镜像部署，不允许复用第一台电脑的绝对路径、虚拟环境或缓存。保存日志、截图、版本信息、镜像大小和 SHA-256。

### 3.3 阶段三：正式实验冻结（08-08—08-16）

先运行 6–12 组预实验，确认参数、输出目录、指标口径、恢复机制和统计脚本。预实验通过后运行正式 360 组矩阵。每组包含唯一 `run_id`、配置快照、日志、指标和状态；失败组定向重跑，不覆盖成功结果。冻结原始结果、汇总表、统计检验、图表和文件清单。

### 3.4 阶段四：正式材料冻结（08-17—08-25）

基于冻结数据生成 Word/PDF 报告、PPT、图表、演讲稿、视频分镜和实际场景演示方案。报告先锁定事实和数据，再处理版式。PPT 与视频只使用报告中可追溯的结论，不单独创造更强表述。

### 3.5 阶段五：提交包冻结（08-26—08-31）

完成视频录制与剪辑，在全新目录执行一次端到端演练，核对文件命名、链接、中文字体、图片分辨率、音画同步和压缩包结构。生成材料清单和校验值，在本机与第二台电脑各保存一份最终包。09-01 只执行上传和结果确认。

## 4. 人机分工

AI 负责代码修改、测试、实验执行与恢复、统计分析、图表、报告和 PPT 初稿、视频脚本、检查清单、证据整理以及每日状态更新。

项目主导人负责 Docker 安装授权与必要的系统操作、第二台电脑配合、学校和团队信息、署名与版权信息、报告和 PPT 的事实审批、真人讲解录制、比赛账号操作及最终上传。

任何需要主导人介入的事项必须提前至少一天列入状态表，并说明所需时间、输入和验收结果，避免 AI 工作流在外部操作处静默等待。

## 5. 验收门槛

### 5.1 质量基线

- 完整测试为 198 passed、0 failed。
- `git diff --check`、Python 编译检查和代码规范检查通过。
- FixedTime、Actuated、CA-MP 均完成最小 SUMO 实跑。
- README、部署文档、命令和实际分支名称一致。
- 证据记录 Git commit、环境版本、命令、退出码和时间。

### 5.2 部署与复现

- Docker 镜像无缓存构建并成功启动。
- API 健康检查和至少一次仿真请求成功。
- 镜像导出、导入后仍可运行。
- 第二台电脑从干净副本完成源码和 Docker 两条复现路线。
- Docker live 和 second-machine reproduction 均有真实证据并标记为 `pass`。

### 5.3 正式实验

- 矩阵严格包含 360 个预期组合且无重复覆盖。
- 每组产物包含运行身份、配置、日志、指标和完成状态。
- 中断可恢复，失败可定向重跑，缺失精确量保持 JSON `null`。
- 汇总表行数、成功/失败状态与原始目录一致。
- 每个报告数字和图表均记录来源文件及生成命令。
- 紧急刹车、碰撞、传送和相位警告单独统计并解释。

### 5.4 正式材料

- 报告覆盖需求、方法、系统、实验、统计、创新、局限和复现。
- PPT 结论可在报告或数据中定位。
- 视频脚本时长为 5–8 分钟，覆盖问题、创新、系统、结果和总结。
- 场景演示方案包含输入、步骤、观察指标、异常处理和备用方案。
- 未经证据支持，不使用“已验证”“显著提升”等确定性表述。

### 5.5 最终提交

- 全新目录按 README 完成从安装到运行的演练。
- 提交包不含缓存、临时结果、个人绝对路径、密钥或无关大文件。
- 文档、链接、字体、图片、视频均可正常打开和播放。
- 解压后存在清晰入口、材料清单和校验值。
- 至少存在两份彼此独立的最终备份。

## 6. 数据流与证据链

正式证据链为：

```text
冻结代码 commit
  → 配置快照与运行矩阵
  → run-scoped 原始产物
  → 审计后的汇总表
  → 统计检验与图表
  → 报告结论
  → PPT 与视频表述
  → 最终提交清单和 SHA-256
```

后级成果只消费已冻结的上级成果。若代码、配置或指标口径发生变化，受影响的实验、统计、图表和材料必须重新生成，不能仅手工改写最终数字。

计划使用以下控制位置：

- `docs/tasks/submission-progress.md`：每日状态、阶段门禁和主导人待办。
- `output/evidence/`：测试、Docker、第二机器与实验验证证据。
- `output/deliverables/`：最终报告、PPT、视频、演示方案和提交清单。

生成物只按明确清单窄范围归档，不把整个临时输出目录无选择提交到 Git。

## 7. 错误处理与恢复

1. 测试或质量门禁失败时暂停后续阶段，先恢复绿色基线。
2. 单组实验失败时记录错误类型和重试次数，仅定向重跑失败组合。
3. 正式结果不支持预期结论时调整结论，不修改样本选择或隐瞒不利结果。
4. Docker 阻塞超过一天时保留本地部署路线作为演示备用，但 Docker 状态继续保持未通过，直到取得真实证据。
5. 第二机器失败时按绝对路径、依赖版本、编码、权限和缓存顺序排查。
6. 运行时间超出预算时优先调节安全并行度和恢复策略，不静默缩减矩阵。
7. 材料延期时立即取消可选加分项，优先保证报告、PPT、代码、运行说明和视频脚本。
8. 每日增量备份；每个阶段冻结时生成独立压缩包和 SHA-256 清单。

## 8. 执行节奏

每日循环为“检查状态—选择唯一主任务—AI 执行—自动验证—保存证据—主导人审核—更新进度—备份”。每天只设一个必须完成的主目标，并记录已完成、验证结果、失败原因、次日目标和截止风险。

每个阶段至少预留一天缓冲。阶段验收使用明确的命令输出和文件证据，不能用“基本完成”“应该可用”等主观描述替代。若阶段延期，首先取消可选项，其次压缩材料润色轮次，不削弱测试、正式实验和可复现性门槛。

## 9. 最终定义

项目只有在代码可运行、实验可追溯、部署可复现、材料相互一致、提交包经过全新环境演练且完成备份后，才可标记为完成。单独通过代码测试、保留历史验收记录或生成材料草稿，均不等同于完成。
